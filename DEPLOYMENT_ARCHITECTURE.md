# Deployment Architecture — Prisoners DAOlemma

**Status:** recommended v1 deployment plan
**Date:** 2026-03-20
**Launch target:** Base mainnet
**Current public live proof:** Base Sepolia

## Executive summary

For the first mainnet-facing release, the right stack is:

- **Frontend:** Vercel-hosted Next.js app
- **Wallet + chain reads:** wagmi/viem in the app, pointed at paid Base RPC endpoints
- **Canonical game data for the site:** static published JSON artifacts under `packages/nextjs/public/games/`
- **Artifact generation:** batch publisher script built on top of the repo's existing query/export tooling
- **Ops/auth/deploy:** existing Foundry + CLI flow from a controlled operator environment
- **Future upgrade path:** add a small ingest worker + object storage only when freshness requirements justify it

The important product decision is: **do not make the public site reconstruct history directly from RPC at page load**. Publish canonical per-game artifacts first, then let the site read those artifacts quickly and reliably.

## Recommended v1 stack

### Web app
- Host `packages/nextjs` on **Vercel**
- Keep the public experience fast and cacheable
- Treat the public app as a reader of published artifacts, not as the primary indexer

### RPC
Use a paid RPC provider for Base:
- **Primary:** Alchemy or QuickNode
- **Backup:** a second provider for failover

Split usage by role:
- **frontend read RPC** for wallet connections and lightweight live reads
- **operator / export RPC** for query/export jobs and deployment tooling

Do not rely on public/shared RPC for launch traffic.

### Data publishing
Use the repo's existing evidence pipeline as the source of truth:
- `packages/foundry/scripts-js/queryTooling.js`
- `packages/foundry/scripts-js/queryCli.js`
- existing exported artifacts like:
  - `game-summary.json`
  - `rounds.json`
  - `messages.jsonl`
  - `payouts.json`
  - `roster.json`
  - `causes.json`
  - `auth.json`
  - `export-manifest.json`

Add one more thin layer:
- a **batch publisher** that scans export bundles and writes web-ready static assets into:
  - `packages/nextjs/public/games/index.json`
  - `packages/nextjs/public/games/<slug>/...`

### Storage
For the first public version, storing published artifacts in the repo build output is enough.

If artifact volume or freshness needs grow, move the exact same published files to:
- **Cloudflare R2** or **S3-compatible object storage**

Use object storage before introducing a full database-backed indexer.

### Optional later additions
Only add these after the first mainnet-facing product surface is working:
- small always-on ingest worker
- Supabase / Postgres cache for query convenience
- websockets / live subscriptions
- richer cross-game analytics backend

## Why this is the right plan

### 1. It matches the repo as it exists today
The repo is already **artifact-first**.

It already knows how to export:
- game snapshots
- round history
- payout history
- auth state
- chat messages

So the fastest reliable product path is to publish those artifacts for the web, not to replace them with a new infrastructure layer immediately.

### 2. It is the simplest path to a good UX
The public product should answer:
- what is this?
- show me a concrete game
- let me inspect and download the data

That is much easier if the app consumes stable published JSON files rather than stitching complex history from RPC in the browser.

### 3. It supports mainnet launch without overbuilding
Mainnet launch target does **not** mean the app must start with a long-running bespoke indexer.

For v1, the right tradeoff is:
- conservative onchain protocol
- conservative ops
- simple artifact publishing pipeline
- strong observer/research UX

## Data flow

## Current flow
1. Contracts emit events onchain.
2. Existing query/export tooling builds evidence bundles.
3. Evidence bundles are stored in the repo or generated by operators.

## Recommended public flow
1. Run export tooling after canaries, rehearsals, or mainnet games.
2. Run the new games publisher.
3. Publisher copies/normalizes artifacts into `packages/nextjs/public/games/`.
4. Next.js pages read only the published web artifacts.
5. Judges/researchers browse games, inspect data, and download artifacts directly.

## Future freshness flow
If later you need near-real-time publishing:
1. small worker polls new blocks / logs
2. worker regenerates exports after meaningful transitions
3. worker publishes the same artifact shape to object storage
4. web app reads from storage-backed public URLs

The public app should still consume the **same artifact model**.

## Launch phases

## Phase 1 — ship now
Deliver:
- homepage with clear explanation + route to games
- `/games` index page
- `/games/[slug]` detail page
- published JSON artifacts in `public/games`
- download links for raw evidence files
- Vercel-hosted app

This is the minimum strong public product.

## Phase 2 — mainnet cutover
Deliver:
- Base mainnet deploy artifacts
- updated contract addresses in public metadata
- published mainnet game exports alongside Sepolia proof
- mainnet observer pages using the same UI/data model

Sepolia remains useful as historical proof; mainnet becomes the live target.

## Phase 3 — freshness / scale improvements
Only after the public product is working:
- object storage for artifacts
- scheduled export/publish jobs
- small ingest worker
- optional DB cache
- richer research/comparison views

## Hosting recommendation

## Public site
**Vercel**

Why:
- already fits the Next.js app
- low-friction previews
- easy environment variable management
- static/public artifacts work naturally

## Operator / export environment
Run Foundry + export/publish tooling from:
- a trusted VPS,
- a controlled workstation,
- or a CI job with explicit secrets handling

Keep deployer / verifier keys out of Vercel.

## Build / publish commands

Recommended public build sequence:
1. `yarn games:publish`
2. `yarn next:build`

Recommended operator sequence for mainnet launch prep:
1. `yarn prod:gates`
2. `yarn prod:base:preflight`
3. `yarn prod:base:deploy`
4. `yarn prod:base:verify`
5. regenerate/publish game artifacts after live runs

## Environment variables

## Frontend
Suggested Vercel env vars:
- `NEXT_PUBLIC_TARGET_NETWORK=base`
- `NEXT_PUBLIC_ALCHEMY_API_KEY=<key>` or equivalent provider key
- `NEXT_PUBLIC_WALLET_CONNECT_PROJECT_ID=<id>`

Optional later:
- `NEXT_PUBLIC_GAMES_DATA_BASE_URL=<external artifact base URL>` if artifacts move out of repo/public

## Operator / export side
Keep these outside Vercel:
- deployer private key / keystore
- verifier EOA key material
- RPC keys for production export jobs if separated from frontend
- treasury / owner / verifier operational secrets

## Risks and mitigations

### Risk: browser-side indexing becomes slow or flaky
Mitigation:
- avoid browser-side historical reconstruction for game pages
- publish normalized artifacts instead

### Risk: wrong network framing in public copy
Mitigation:
- always present **Base mainnet** as launch target
- present **Base Sepolia** as current public proof / rehearsal evidence until mainnet games exist

### Risk: overbuilding infra before product fit
Mitigation:
- start with batch publishing
- add worker/storage only when needed

### Risk: deploy/auth ops become mixed into public hosting
Mitigation:
- keep Vercel strictly for public web
- keep deploy/auth/export operations in a separate controlled environment
